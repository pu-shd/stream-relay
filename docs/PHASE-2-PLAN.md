# Phase 2 — Infrastructure, scripts, and the first real deploy

Phase 0–1 gave a verified relay that runs locally. Phase 2 makes it deployable to Azure and,
crucially, **provably tearable-down** — because the whole design is a cold standby.

Scope: Bicep resources, the four resumable scripts, the mock-`az` suite, then one real deploy on
the `*.azurefd.net` hostname that is torn down the same day.

## 2. Blocking corrections to Phase 0/1 artifacts

These must land before any Bicep is written, because the generated config is currently wrong.

### 2.1 The Front Door hostname cannot be predicted — and must survive teardown

`render-relay.py` currently emits `RELAY_HOST=orfe-relay.azurefd.net`. **That hostname will never
exist.** Front Door Standard endpoint hostnames are
`<endpointname>-<pseudorandom-hash>.z01.azurefd.net` — the hash is deliberate, to prevent
subdomain takeover. So the real hostname is only knowable *after* deployment.

This is much worse for a cold standby than it first appears: **if the hash changes on every
teardown/redeploy, every Apple TV's `vlc.xml` breaks on reactivation** — precisely the moment
you cannot afford surprises.

Fix, three parts:

1. **Set `autoGeneratedDomainNameLabelScope`** on the endpoint so the hash is *reused* across
   delete-and-redeploy. Front Door supports `TenantReuse` (default) / `SubscriptionReuse` /
   `ResourceGroupReuse` / `NoReuse`. Pin it explicitly to `TenantReuse` and never leave it
   implicit — the entire teardown/redeploy cycle depends on it.
2. **Stop fabricating the hostname.** Add `azure.frontdoor_hostname: null` to `relay.yml`,
   marked *populated by deploy.sh*. `relay_host()` returns the custom domain if set, else the
   discovered hostname, else a sentinel that is obviously not a real host. A new
   `discover-hostname` step reads `az afd endpoint show --query hostName`, writes it back, and
   re-renders.
3. **The DNS block must not print a fake CNAME target.** `--print-dns` currently emits
   `CNAME stream → orfe-relay.azurefd.net`. It must refuse to emit a CNAME until the real
   hostname is known, or it will send a wrong record to Princeton DNS.

New tests: `relay_host()` never returns a bare `<endpoint>.azurefd.net`; `--print-dns` errors when
`frontdoor_hostname` is null and `domain` is set; the reuse scope is asserted present in the Bicep.

**This is also the strongest argument yet for getting `stream.orfe.princeton.edu` early** — a
custom domain makes consumers independent of the hash entirely.

### 2.2 Resource naming diverges from the established convention

Existing groups in this subscription follow `orfe-dept-azure-<project>-rg`
(`orfe-dept-azure-meet-rg`, `-graddb-rg`, `-thesis-rg`). `relay.yml` currently says
`rg-orfe-stream-relay`, which matches nothing here.

**Decided: adopt the convention.** Rename to **`orfe-dept-azure-relay-rg`** and align the rest.
Watch the platform limits while renaming: Key Vault names are max 24 chars and globally unique;
ACR names are alphanumeric-only and globally unique (`acrorfestreamrelay` is confirmed available).

### 2.3 Region: `eastus` (decided)

Most existing ORFE resources are in **canadacentral**; a few are in **eastus**. `D4s_v6` is
available in both, with 350 vCPU quota and 0 used in `eastus`.

**Decided: `eastus`** — far closer to Princeton (Virginia vs Toronto), which matters for SRT
ingest RTT and retransmission behaviour on a UDP protocol, and it matches every cost figure
computed so far. This is a deliberate divergence from the departmental default; record it in the
README so the next person does not "fix" it.

## 3. Bicep module structure

```
infra/
├── main.bicep                  # orchestrator (params contract already committed)
├── main.bicepparam             # ← generated, lives in the config repo
└── modules/
    ├── identity.bicep          # UAMI + federated credential
    ├── keyvault.bicep          # vault, RBAC auth, secret placeholder
    ├── acr.bicep               # registry + AcrPull/Repository Reader for the UAMI
    ├── network.bicep           # vnet, subnet, NSG, STATIC public IP
    ├── vm.bicep                # VM + cloud-init + UAMI attachment
    ├── frontdoor.bicep         # profile, origin group, origin, route, rules, WAF
    └── guardrails.bicep        # budget + anomaly alert
```

Non-obvious constraints, each already recorded as a `TODO(phase-2)` in `main.bicep`:

- **Cache key must ignore `session`.** MediaMTX appends `?session=<uuid>` per viewer in every
  `hlsVariant`. Without *Ignore Specified Query Strings*, hit rate is ~0 and origin egress roughly
  doubles the bill.
- **Cache TTL must be explicit** on `*.m3u8`. MediaMTX sends no `Cache-Control`, and Front Door
  then picks a **random 1–3 day TTL**, which would pin a stale playlist for days. Short TTL on
  manifests, long on segments.
- **Public IP must be static.** The page-stream producers embed it in their ingest URLs; a dynamic
  IP silently breaks every publisher on VM restart.
- **NSG opens only** `8890/udp` (ingest) and `8888/tcp` from the `AzureFrontDoor.Backend` service
  tag. MediaMTX's API (9997) and metrics (9998) are loopback-bound in the generated config and get
  no NSG rule, ever.
- **Budget is provisioned in Bicep**, not by hand, so a teardown/redeploy cycle cannot silently
  drop the cost guardrail.
- **WAF rate-limit** is a Front Door *Standard* custom rule (confirmed: only managed rule sets
  need Premium).

there is exactly one code path to test.

| # | Step | Idempotency check | Notes |
| :--- | :--- | :--- | :--- |
| 1 | `preflight` | — | Tools, versions, login, subscription, **Owner/UAA role**, quota for the *derived* SKU, provider states |
| 2 | `register-providers` | `az provider show` | **New.** `Microsoft.Cdn` is NotRegistered; poll to `Registered` |
| 3 | `resource-group` | `az group exists` | |

### Resumable state machine

```jsonc
// .stream-relay-state.json (gitignored)
{
  "schema": 1,
  "subscription": "<subscription-id>",
  "resource_group": "orfe-dept-azure-relay-rg",
  "steps": {
    "resource-group": { "status": "done", "at": "…", "ids": { "rg": "/subscriptions/…" } },
    "front-door":     { "status": "failed", "at": "…", "error": "…" }
  }
}
```

Rules, in priority order:

1. **Every step re-queries Azure before acting.** State is an *accelerator*, not the source of
   truth — deleting the state file must still converge. This is what makes a 24–48 h certificate
   wait survivable across days and machines.
2. **State is written only after verification**, never before acting, so a step is never recorded
   half-done.
3. `trap` on `ERR`/`INT` records the failed step and prints the literal `--from <step>` command.
4. Flags: `--resume`, `--step`, `--from`, `--list-steps`, `--reset-state`, `--dry-run`.
5. Slow steps poll with a spinner, a real timeout, and a statement of what they are waiting on.

`--dry-run` runs `az deployment group what-if` and mutates nothing — the safe rehearsal before
first spend.

## 5. Mock-`az` test suite

```
tests/mock-az/
├── bin/az                  # shim placed first on PATH
├── fixtures/               # canned JSON per (command, scenario)
├── scenarios/
│   ├── fresh/              # nothing exists
│   ├── partial/            # steps 1-9 done, 10 failed
│   ├── existing/           # everything exists (idempotency)
│   └── cdn-unregistered/   # mirrors this subscription's real state
└── run.sh
```

The shim records every invocation to `$MOCK_AZ_LOG`, so tests assert on argv. Cases:

- **Idempotency** — a second full run issues **zero** mutating calls (no `create`/`update`/`delete`).
- **Resumability** — kill at step *n*, `--resume`, and steps 1..*n*-1 issue no mutating calls while
  *n*..16 complete.
- **State-free convergence** — delete the state file mid-run; `--resume` still converges.
- **Teardown ordering** — Front Door before VM before network; `--soft` leaves ACR/KV/UAMI intact;
  `--hard` deletes the group.
- **Fail-closed** — `preflight` aborts on Contributor-only role, insufficient quota, or an
  undersized pinned `vm_size`.
- **Provider registration** — the `cdn-unregistered` scenario must trigger step 2, not fail at 12.
- **No secret leakage** — scan the recorded log: the passphrase must never appear in an `az` argv
  (it goes via `--file`/stdin, since argv is visible in process listings).

Runs offline in CI. `tests/bicep/` adds `az bicep build` plus a real `what-if` behind `LIVE=1`.

## 6. First real deploy — deferred (decided)

**Phase 2 stops at `--dry-run`. Nothing is created; spend stays $0.** The build ends with
`az deployment group what-if` run against the real subscription, which validates the Bicep and the
parameter binding without provisioning anything. The real deploy is a separate, explicitly
approved step.

```bash
scripts/deploy.sh --dry-run          # ← Phase 2 ends here. what-if only, zero spend.
# --- separate approval boundary ---
scripts/bootstrap.sh                 # interactive, real
scripts/verify.sh                    # assert HLS end-to-end via Front Door
scripts/teardown.sh --soft           # back to ~$5/mo, same day
```

Consequence to accept honestly: `what-if` validates *shape*, not *behaviour*. Everything in the
verification list below — the cache-hit assertion, the hostname-stability check — remains
**unproven** until the real deploy happens. The riskiest items in §7 are precisely the ones
`what-if` cannot cover, so Phase 2 completing green is not the same as the fallback working.

When that approval comes, verification must assert, against the **Front Door hostname** (not the
VM):

- every relay path serves a valid manifest, and ffprobe decodes 1080p h264+aac;
- a second request for the same manifest is a **cache hit** (`X-Cache`), proving the `session`
  query-string rule works — the single most expensive thing to get wrong;
- manifests carry the explicit short TTL, not a random multi-day one;
- `8890/udp` accepts an encrypted publish and **rejects** an unencrypted one;
- ports 9997/9998 are **not** reachable from the internet;
- teardown `--soft` then `bootstrap.sh --resume` returns the **same** hostname (proves the reuse
  scope) and passes verification again.

**Cost of this exercise:** a D4s_v6 at $0.202/hr plus prorated Front Door base — roughly
**$1–2 for a few hours**, then back to ~$5/mo. Budget alerts are provisioned at step 14, before
any traffic.

## 7. Risks

| Risk | Mitigation |
| :--- | :--- |
| AFD hash changes on redeploy → Apple TVs break | Pin `autoGeneratedDomainNameLabelScope`; verification explicitly tests teardown→redeploy hostname stability |
| Cache rule wrong → egress ~2× | `X-Cache` hit assertion in `verify.sh`, not just a config review |
| `Microsoft.Cdn` registration is slow/fails | Dedicated step 2 with polling, before anything depends on it |
| Passphrase leaks via `az` argv | Pass by file/stdin; mock suite scans the recorded argv log |
| Teardown leaves orphans, quietly costing money | `teardown.sh` re-queries and reports every surviving resource; rehearsal drill exercises it |
| Key Vault soft-delete blocks redeploy of the same name | Use `--enable-purge-protection false` for a standby, and handle "vault exists in soft-deleted state" in step 6 |
| `--hard` teardown run by accident | Requires typing the resource-group name; `--yes` only for CI |

## 7b. Outcome (2026-07-29)

Phase 2 delivered. Findings from building it, beyond the two anticipated in §2:

1. **macOS ships bash 3.2, and three scripts used bash 4+ constructs** (`${VAR^^}`, `mapfile`).
   They failed immediately on the primary development platform. All scripts are now 3.2-safe, and
   CI greps for the constructs so they cannot creep back in — Ubuntu's bash 5 would happily run
   them and hide the breakage.
2. **`--dry-run` printed "✓ created resource group" without creating anything.** A cosmetic bug
   with real consequences: the whole value of a dry run is trusting what it reports. Fixed, and
   the completion banner now distinguishes `--dry-run` from `--dry-run --allow-rg`.
3. **`what-if` cannot run without an existing resource group**, and azure-cli 2.88 *crashes*
   while rendering the resulting error (`RuntimeError: The content for this response was already
   consumed`), burying the cause entirely. Added `--allow-rg` to create just the free empty group,
   plus a `validate` fallback that surfaces the real error when the CLI bug strikes.
4. **`what-if` evaluated `Microsoft.Cdn` resources while the provider was NotRegistered.** So a
   clean what-if is *not* evidence the deployment will succeed — vindicating `preflight` and
   `register-providers` as distinct steps rather than trusting the template check.
5. Two shell bugs shellcheck could not see: a `test` missing its closing `]` (the provider wait
   would have spun to timeout), and a function whose last command returned non-zero on the
   *success* path, which would have recorded a false step failure.
6. `az acr build` replaced a local `docker push`: building server-side avoids producing an arm64
   image on a Mac for an amd64 VM.

Verified against `ORFE-dept-azure`: preflight passes (Owner, 350 vCPU free), Bicep and the
generated `.bicepparam` compile, and what-if reports **22 resource creations** plus 2
`Unsupported` (nested role assignments, a documented what-if limitation, not an error).
